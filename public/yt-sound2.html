Round two: never change the source

Round one proved that swapping a media element's src throws away the tap's permission. These two never swap it. Same rules: one tap to arm, then hands off for 6 seconds while it fires itself and checks that real sound is coming out.

Before you start

Check the phone's ring/silent switch is on RING and that Low Power Mode is OFF, then note which they were. Both silence audio on their own and would read as a failure here. This matters for the real effect too: a borrowed phone on silent plays nothing whatever we build.

4 · Web Audio, no element at all

The tap starts an AudioContext. There is no src to invalidate, so the permission has nothing to lose. The song is fetched, decoded and played into that running context afterwards. This is how web instruments and games make sound on iOS.

5 · One stream, held open by the server

The tap points an audio element at an endpoint that answers immediately with silence and keeps the connection open, then splices the song onto the same response. The element plays one continuous stream and its src never changes.
